# Изменение контрактов

Контракт читают три приложения и вкладки браузера со старым фронтом. Ломающая правка не всегда видна компилятору: старая вкладка упадёт уже у пользователя. Контракт, бэк и фронт меняем одним PR.

## 1. Найди место

- `common/`: id, роли, права, лимиты, коды ошибок, пагинация. `http/`: DTO по ресурсам. `ws/`: события и версия протокола. `board/`: элементы доски. `ai/`: плоские схемы ответов модели.
- Для данных пишем схему, тип выводим через `z.infer`. Отдельный `interface` только для карты событий сокета.

## 2. Измени совместимо

- Новое поле: `.optional()` или `.default(...)`.
- Для данных между приложениями не используй `z.strictObject`: новое поле уронит старый парсер. Обычный `z.object` лишние поля отбрасывает.
- Даты: `z.iso.datetime()` (не `z.string().datetime()` и не `z.date()`), без `transform`: иначе ломается `z.toJSONSchema`.
- Новое значение перечисления или новый тип в объединении старый фронт не распознает. Напиши в PR, что увидит открытая вкладка со старым кодом.
- Удалить или переименовать поле, сменить тип, сделать поле обязательным можно только через ADR (скилл `project-adr`) и новую версию протокола в `ws/`. Бэк тогда выкатываем раньше фронта.

## 3. Обнови потребителей в том же PR

- `apps/api`: входные данные проверяются той же схемой; ответ ей соответствует.
- `apps/web`: запросы в `shared/api`, формы (`zodResolver`), обработчики событий сокета.
- `apps/worker` и схемы ИИ, если их задело.

## 4. Проверь

- Typecheck всех пакетов, которые импортируют contracts, одной задачей turbo (с каркасом): она сначала пересоберёт contracts. Запускаешь tsc в пакете вручную: сначала собери contracts, иначе проверка пойдёт по старому `dist`.
- Тест схемы: валидный и невалидный пример; payload в старом формате всё ещё проходит.
- Изменилась схема ИИ: `z.toJSONSchema` строится без ошибок.

Справка: https://zod.dev/llms.txt (только API Zod 4); раздел 5 в `docs/architecture/frontend.md`.
