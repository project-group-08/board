# Сервис совместной работы на интерактивных досках

Бесконечный холст, совместное редактирование в реальном времени, функции ИИ.

## Структура

| Папка                        | Что внутри                                          |
| ---------------------------- | --------------------------------------------------- |
| `apps/web`                   | фронтенд: Next.js 16, слои FSD 2.1                  |
| `apps/api`                   | бэкенд: NestJS 12, Socket.IO, Prisma 7              |
| `packages/contracts`         | общие схемы Zod и типы для фронтенда и бэкенда      |
| `packages/board-doc`         | документ доски на Yjs                               |
| `packages/board-engine`      | движок доски, отрисовка на Konva (планируется)      |
| `packages/typescript-config` | общие настройки TypeScript: база и React-библиотеки |
| `docs/`                      | архитектура, решения (ADR), правила для ИИ-агентов  |

Подробно: [docs/architecture/frontend.md](docs/architecture/frontend.md).

## Начало работы

1. Node.js из `.nvmrc` (например, `nvm install && nvm use`) и pnpm: `corepack enable pnpm`.
2. `pnpm install`.

Нужны Node.js 24 (от 24.15) и pnpm 12; версии закреплены в `.nvmrc` и `packageManager`.

### Запуск приложений

`pnpm dev:web` запускает Next.js на <http://localhost:3000>.

`pnpm dev:api` запускает NestJS на <http://localhost:4000> с перезапуском
при изменениях. Для авторизации настройте `apps/api/.env` по шаблону,
поднимите локальные PostgreSQL и Mailpit. Примените миграции из корня проекта
командой `pnpm --filter @tabula/api exec prisma migrate deploy`. Запуск и сборка
генерируют клиент Prisma и собирают контракты.

`pnpm dev` запускает оба приложения через Turborepo. Команды
`pnpm build:web` и `pnpm build:api` собирают приложения отдельно.
`pnpm build` собирает оба приложения вместе с доступными сборками зависимостей.
После сборки используйте `pnpm start` для обоих приложений
или `pnpm start:web` и `pnpm start:api` по отдельности.
При запуске собранного API команда `start` читает `apps/api/.env`. За Caddy
укажите адрес или подсеть доверенного прокси в `TRUSTED_PROXY`, чтобы лимит
отправки писем применялся по IP посетителя.

В соответствии с ADR-0004 браузер должен обращаться к API через Caddy:
`/api` и `/socket.io` направляются в NestJS, остальные пути в Next.js.
Порты 3000 и 4000 предназначены для отдельных процессов; CORS и rewrites
в Next.js не включены. Конфигурацию Caddy добавляет задача инфраструктуры.

Укажите в `APP_URL` внешний адрес приложения. При подтверждении ссылки,
обновлении сессии, выходе и изменении профиля API сверяет `Origin` запроса
с этим адресом, включая протокол и порт. Подтверждение ссылки принимает
тело в JSON.

Проверки приложений:

- `pnpm --filter @tabula/web check-types`: `next typegen` и TypeScript.
- `pnpm --filter @tabula/web lint:fsd`: границы FSD через Steiger.
- `pnpm --filter @tabula/api check-types`: TypeScript бэкенда.
- `pnpm test:api`: разовый прогон Vitest. База и доставка писем в тестах подменяются.

Линт и форматирование настраиваются в корне репозитория
([ADR-0010](docs/adr/0010-root-lint-format-config.md)); инструменты выбраны
в [ADR-0007](docs/adr/0007-oxlint-oxfmt.md).

| Что проверяем                               | Где настраиваем      | Команда из корня    |
| ------------------------------------------- | -------------------- | ------------------- |
| Правила кода и проверки с учётом типов      | `.oxlintrc.json`     | `pnpm lint`         |
| Формат, порядок импортов и классов Tailwind | `.oxfmtrc.json`      | `pnpm format:check` |
| Границы FSD фронтенда                       | Steiger в `apps/web` | `pnpm lint:fsd`     |

- `pnpm format`: форматирование Oxfmt, включая сортировку импортов и классов Tailwind (`cn`, `cva`, `clsx`).
- `pnpm format:check`: проверка форматирования без записи.
- `pnpm lint`: Oxlint для всего репозитория, включая корневые файлы и скрипты.
- `pnpm --filter @tabula/web lint` и `pnpm --filter @tabula/api lint`: те же правила для одного приложения. В пустых пакетах команды проверок добавляются вместе с исходниками.
- `pnpm lint:fsd`: отдельная проверка архитектуры фронтенда; известные замечания к каркасу описаны в `docs/ai/README.md`.
- `pnpm check-types`: проверка типов через Turborepo.

Oxlint, его движок проверки типов, Oxfmt и JS-плагин Turborepo установлены
в корневом `package.json`. Их версии закреплены в catalog в
`pnpm-workspace.yaml`; версии Oxc заданы точно. Плагин `eslint-plugin-turbo`
исполняется самим Oxlint и проверяет `turbo/no-undeclared-env-vars`;
установка ESLint для него не нужна. Для редактора используется расширение
`oxc.oxc-vscode`.

Общие настройки TypeScript подключаются через `extends` из
`@tabula/typescript-config/base.json`. Настройки Next.js находятся в
`apps/web/tsconfig.json`, настройки NestJS находятся в `apps/api/tsconfig.json`.
Пути исходников, псевдонимы, `include` и `outDir` также остаются в конфигурациях
приложений. Базовая конфигурация не подключает глобальные типы; Node.js включён
явно в конфигурациях обоих приложений. Для React-библиотек в общем пакете
есть `react-library.json`, который расширяет базу.

В `.oxlintrc.json` находятся общие правила, исключения сборочных каталогов,
проверка с учётом типов и запрет предупреждений. Отличия задаются там же
через `overrides`: правила Next.js действуют в `apps/web`, браузерные
глобальные переменные разрешены в web и `packages/ui`. Это позволяет
проверять одинаковые правила из корня, из пакета и в редакторе.
Скрипты `lint` в пакетах явно указывают корневой конфиг и ограничивают
проверку текущей папкой. Отдельных конфигов линта в приложениях и пакета
`oxlint-config` нет. Форматирование также едино для всего репозитория.
Корневые конфиги учтены в кэше Turborepo.

Пакеты `contracts`, `board-doc` и `ui` пока не содержат исходников; команды
проверки типов и сборки для них добавляются вместе с первым кодом.
`board-engine` будет возвращён отдельной задачей; web пока не зависит от него.

`AGENTS.md` исключены из форматирования: форматирование таблиц увеличивает их размер сверх лимита цепочки правил для Codex. Выгрузку архитектуры `docs/architecture/frontend.md` обновляем только из исходной доски.

Остальные проверки появятся вместе с конфигами: список работ в [docs/ai/README.md](docs/ai/README.md), раздел «Сделать с каркасом».

## Ветки и коммиты

- `main`: стабильная версия, с неё деплой на прод. `develop`: основная ветка разработки.
- Ветка задачи создаётся от свежего `develop`: `feature/<ключ задачи>-кратко`, `fix/<ключ задачи>-кратко`, `chore/<ключ задачи>-кратко`.
- Ветка задачи вливается в `develop` через PR с зелёным CI и ревью. `develop` вливается в `main` через PR, когда версия стабильна и проверена.
- Коммиты по Conventional Commits, например `feat(web): добавить панель версий`.

Подробно: [AGENTS.md](AGENTS.md), раздел «Git и PR», и [ADR-0008](docs/adr/0008-gitflow.md).

## ИИ-агенты и скиллы

Правила для агентов лежат в `AGENTS.md`: общие в корне и свои в каждом приложении и пакете. Их читают Claude Code, Codex, Cursor, Copilot и другие агенты.

Скилл это готовая инструкция для типовой задачи. Агент открывает подходящий скилл сам, по описанию задачи. Вызвать скилл можно и явно: в Claude Code `/project-board-element`, в Codex `$project-board-element`, в остальных агентах словами «открой скилл project-board-element».

| Скилл                      | Что делает                                                                                                             | Когда вызывать                                                              |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `project-setup`            | создаёт каркас: папки по архитектуре, `package.json` пакетов, версии и зависимости фронтенда и бэкенда                 | один раз, при создании репозитория                                          |
| `project-fsd-slice`        | добавляет или переносит страницу, маршрут, слайс или сегмент во фронтенде по FSD                                       | новая страница, виджет, фича или сущность; перенос кода между слоями        |
| `project-contracts-change` | меняет общие схемы Zod так, чтобы не сломать фронтенд, бэкенд и уже открытые вкладки                                   | новая или изменённая схема, DTO, событие сокета, лимит                      |
| `project-socket-event`     | проводит событие Socket.IO от схемы до обработчиков на бэкенде и фронтенде                                             | новое событие реального времени: правка доски, курсоры, комментарии, доступ |
| `project-board-element`    | добавляет тип элемента доски или инструмент через все слои: схема, проверка на бэкенде, документ, отрисовка, интерфейс | новый элемент (стикер, фигура, стрелка) или инструмент                      |
| `project-review`           | проверяет изменения по правилам проекта: границы слоёв и пакетов, контракты, состояние, права, секреты, тесты          | перед открытием PR и при ревью чужого PR                                    |
| `project-adr`              | записывает архитектурное решение в `docs/adr`                                                                          | команда приняла, изменила или отменила решение                              |

Пример запроса агенту: «/project-board-element добавь на доску элемент "таблица"». Как устроены правила и что читает каждый агент: [docs/ai/README.md](docs/ai/README.md).
